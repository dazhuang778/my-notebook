# Agent 编排模式梳理与总结

## 一、从简单提示到智能体模式

Agent 编排模式的核心意义在于：让大模型不再像传统的 Prompt 堆叠那样一次性被动输出，而是具备自主规划、执行与反思能力，系统性地提升任务处理的可靠性。传统的 Prompt 工程具有静态性、知识边界受限、缺乏反思等局限，而 Agent 模式通过架构设计突破这些限制，实现了从静态调用到动态智能体系统的跨越。从架构方法论来看，Agent 编排可分为两大路径：一是 **Workflows（工作流）**，即 LLM 与工具通过预定义的代码路径进行编排，更偏规范性；二是 **Agents（智能体）**，即 LLM 动态决定自身的处理流程与工具使用方式，更偏自主性。

目前业界对这些模式有多种归纳角度，但总体上可以分为**单 Agent 内部编排模式**（聚焦于单个智能体如何思考、行动与自我修正）和**多 Agent 协作编排模式**（聚焦于多个智能体如何分工、协调与信息共享）。



## 二、单 Agent 内部编排模式

单 Agent 的内部编排模式决定了智能体如何组织自己的“思考-行动”循环，是编排设计的最基础层面。

### 1. ReAct 模式：推理与行动协同

ReAct（Reasoning + Acting）模式将推理与行动有机融合，形成“思考→执行→观察→再思考”的循环。Agent 并非直接跳到结论，而是在如下阶段之间交替：推理（分析当前信息、识别缺口）、行动（执行工具或查询）、观察（评估结果以决定下一步），直至任务完成。其关键优势在于推理过程的外部化——每一步决策都可见，创建了清晰的审计轨迹，便于追踪失败原因。

- **适用场景**：需要适应性推理的开放任务，如研究代理追踪证据线索、调试助手通过迭代假设诊断问题、客服处理非标准请求。
- **局限**：每一步推理都需要额外的模型调用，延迟和成本较高；如果某一步工具返回错误数据，错误可能传播至后续推理步骤；模型推理能力决定了模式效果的上限。

### 2. 反思模式（Reflection）：自我批判与迭代优化

反思模式在 Agent 输出之上增加了一层自我评估机制。Agent 先生成初始响应，然后以批判者的视角检查准确性、验证规则符合性、识别逻辑缺口，发现任何问题后修正输出并重复这一过程，直至达到质量阈值。其核心在于**角色分离**——强制 Agent 从评判的角度审视自己的输出，而不是一味维护第一次的回答，从而减少确认偏差。

这类模式的典型实现之一是 **Plan-Execute-Reflect** 范式：通过步骤分解、执行和动态调整来解决复杂任务，通常由 Planner（规划者）、Executor（执行者）和 Replanner（重新规划者）三个角色协同完成。更进一步的 **RP-ReAct（Reason-Plan-ReAct）** 架构通过一个 Reasoner Planner Agent 负责规划每一步骤并持续分析执行结果，同时由 Proxy-Execution Agent 将子步骤转化为具体的工具交互。

- **适用场景**：输出质量要求高的场景，如代码审查、事实核查、内容创作中的质量控制。
- **局限与优化策略**：需要给反思 Agent 提供明确而具体的评判标准，否则容易流于形式；必须设置最大迭代次数以防止无限循环。

### 3. 工具使用模式（Tool Use）：扩展能力边界

工具使用模式通过集成外部 API、数据库和计算资源，显著扩展 Agent 的能力范围。典型工具包括知识检索工具（向量数据库、搜索引擎）、计算工具（代码解释器、数学库）和交互工具（API 调用、浏览器操作）。

- **适用场景**：需要实时数据、外部计算或与数字世界交互的任务，如金融分析 Agent 调用实时市场数据 API。

### 4. 规划模式（Planning）：多步骤分解与执行

规划模式让 LLM 能够提出并执行实现目标的多步骤计划——例如撰写论文时，先写大纲，再搜索和研究各部分内容，最后写出草稿。这种模式使 Agent 在面对复杂目标时能够自主分解任务、组织执行顺序。

上述四种模式构成了 AI Agent 工作流的核心架构，被吴恩达教授定义为 Agent 的四大基础设计模式。在实际应用中，这些模式往往叠加使用：工具使用提供能力基础，ReAct 组织核心循环，反思提供质量保证，规划统筹全局目标。



## 三、多 Agent 协作编排模式

当单一 Agent 难以处理多个领域知识的任务，或者不同团队需要独立开发和维护各自的能力时，多 Agent 架构便成为正确选择。这一维度的模式解决的是“多个 Agent 之间如何通信、分工与决策”的问题。

### 1. 编排者-子 Agent 模式（Orchestrator-Subagent）

这是最常用的多 Agent 起点模式。一个编排者 Agent 担任“组长”，负责规划、分配任务和综合结果；子 Agent 各自处理具体工作，通常是**无状态**的，不记忆过往交互。以 Claude Code 为例，主 Agent 负责主要的编码工作，同时在后台派遣子 Agent 搜索大型代码库或调查独立问题，每个子 Agent 拥有自己的上下文窗口并返回精炼后的发现，从而保持主 Agent 的上下文聚焦，探索任务并行进行。

Anthropic 的多 Agent 研究系统采用了这种架构，通过 Claude Opus 4 作为主导 Agent、Claude Sonnet 4 作为子 Agent，在内部研究评估中比单 Agent Opus 4 的表现高出了90.2%。这种架构能跨不同上下文的 Agent 实现并行推理，是单 Agent 无法做到的。

- **适用场景**：任务拆分方式明确、子任务之间依赖关系少、有明确边界的场景，如多领域任务的自动化处理。
- **局限**：编排 Agent 本身可能成为瓶颈，且每次交互多一次模型调用，带来额外延迟和 token 消耗。

### 2. Agent 团队模式（Agent Teams）

多个专门的 Agent 组成团队，在较长时间内并行工作，各自负责独立的工作方向，通过协调机制同步成果。这一模式有两种典型变体：

- **协调模式（Coordinate）**：一个主导 Agent 在团队成员之间委派任务并综合结果。
- **路由模式（Route）**：根据任务将每个请求定向到最匹配的 Agent。
- **适用场景**：需要长时并行运行且子任务独立性高的项目，如多模块代码开发（前端/后端/测试并行推进）。
- **局限**：Worker 之间的冲突管理和完成检测较困难；需要更多基础设施支持（如 AWS 层面的部署）以保证容错性。

### 3. 生成-验证模式（Generator-Verifier）

这是最简单却最实用的多 Agent 模式。Generator 接收任务并产出初始结果，Verifier 按照明确标准检查结果是否达标；如果不通过，Verifier 将具体的修改建议返回给 Generator，循环往复直至通过或达到最大迭代次数。

- **适用场景**：输出质量要求高且验证标准可明确列出的任务，如客服邮件自动回复（一个 Agent 生成回复草稿，另一个检查准确性和品牌语气）。
- **局限**：验证标准若模糊，Verifier 容易形同虚设；必须设置最大迭代次数以防止“生成→拒绝”无限循环。

### 4. 消息总线模式（Message Bus）

引入事件驱动机制，Agent 通过消息总线进行异步通信。每个 Agent 订阅自己关心的事件类型，产生结果后发布新事件，触发链式处理。

- **适用场景**：处理流程需要分支，且 Agent 数量持续增长、需要松耦合的场景。
- **局限**：调试和事件追踪的难度显著上升。

### 5. 共享状态模式（Shared State）

所有 Agent 通过一个共享存储空间来协调，而非通过中心化的编排者或协调者传递信息。这一模式直接去掉了中间人，让所有 Agent 通过共享上下文进行协作。

- **适用场景**：需要相互参考彼此发现来深入探索的协同调查任务。
- **局限**：没有明确的终止条件时容易形成无限循环；并行写入的竞争管理也是一项挑战。



## 四、编排框架中的结构化工作流模式

除上述核心设计模式外，现代 Agent 开发框架（如 Microsoft Semantic Kernel、Google ADK）还提供了一套**预定义的结构化编排模式**，更贴近工程实践中的执行流控制：

- **顺序编排（Sequential）**：Agent 按流水线方式依次处理，每个 Agent 的输出成为下一个 Agent 的输入，适用于文档审核、数据处理管道等多阶段任务。
- **并发编排（Concurrent / Parallel）**：多个 Agent 并行处理同一任务，各自独立执行后汇总结果，适用于头脑风暴、集成推理或投票系统。
- **循环编排（Loop）**：Agent 在显式终止条件下反复迭代执行子 Agent。
- **群聊编排（Group Chat）**：模拟 Agent 之间的协作对话，由群聊管理器控制发言顺序，可引入人工参与，适用于模拟会议和多角色问题解决。
- **交接编排（Handoff）**：Agent 根据上下文将控制权转交给具备相应专长的另一个 Agent，适用于客户支持系统先由通用 Agent 接入再转交技术专家的场景。

这些结构化模式与前面讨论的设计模式并不冲突，而是提供了一种“工程化落地”的方式——例如，Generator-Verifier 模式可以用循环 Agent 实现，Orchestrator-Subagent 模式可以用并发编排配合路由来实现。



## 五、模式选择策略

编排模式的选择并非越复杂越好，业界普遍推荐“**从简单到复杂，按需演进**”的策略。Anthropic 的建议是：从最简单的模式入手，观察它在哪里暴露出局限，再演进到更复杂的模式。LangChain 也同样建议：很多任务用单 Agent 加好工具就足够了，只有在跨领域知识管理、多团队协同开发或任务复杂度超出单 Agent 能力时才引入多 Agent 架构。

选择不同模式时，还需要在以下维度进行权衡：

- **成本**：每次额外的 Agent 调用都会增加 token 消耗
- **延迟**：多步推理和 Agent 间通信会增加整体响应时间
- **可靠性**：更复杂的编排链路引入更多潜在故障点
- **可观测性**：复杂的 Agent 间交互会使调试和追踪难度上升



## 六、总结

Agent 编排模式本质上是对“如何让 LLM 系统化地思考、行动、协作与进化”的系统性回答。从单 Agent 内部循环（ReAct、反思、工具使用、规划），到多 Agent 协作架构（编排者-子 Agent、Agent 团队、生成-验证、消息总线、共享状态），再到框架提供的结构化工作流模式，构成了一个从基础能力到复杂协作的完整编排谱系。

理解编排模式的关键在于把握两条主线：**单 Agent 内部的认知架构**（Agent 如何思考与行动），以及**多 Agent 之间的协调架构**（Agent 之间如何通信与决策）。在工程实践中，成功的编排设计往往从最简单的模式开始，根据实际痛点逐步演进，在功能需求与系统复杂性之间找到最佳平衡点。
